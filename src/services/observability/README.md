# services/observability

Сбор серверных ошибок сайта и воркеров, журнал в админке и письма дежурному. Перенесено из Comersi (`src/server/observability`) и адаптировано под Polet: Postgres/Payload вместо MongoDB, свой `EmailService`, админка Payload вместо отдельного экрана.

## Как устроено

```
точка перехвата
      │
      ▼
captureError(error, context)   синхронный, возвращает errorId, ничего не ждёт
      │  (setImmediate)
      ▼
normalize        очистка сообщения, разбор стека, карты кода
      ▼
raw-store        журнал error-events — ПОЛНАЯ запись, пишется ПЕРВОЙ
      ▼
policy (Redis)   отпечаток, растущая пауза, часовой лимит, всплески
      ▼
safe-payload     БЕЛЫЙ СПИСОК — граница персональных данных
      ▼
queue            BullMQ «error-alerts» (Redis недоступен → отправка сразу)
      ▼
alert-worker     в веб-приложении → EmailService → ERROR_ALERT_EMAIL
```

«Сначала запись, потом доставка»: недоступная почта означает «узнаю позже», а не «не узнаю никогда».

## Две половины и гейт персональных данных

| | Где | Что |
|---|---|---|
| **Сырая** | коллекция `error-events`, группа `raw` | исходный текст ошибки, причины, полный стек, пользователь, IP, User-Agent, фактический путь с query, контекст |
| **Безопасная** | письмо, очередь в Redis, суточная сводка | класс ошибки, очищенное сообщение, урезанный стек, модуль, **шаблон** маршрута, псевдоним пользователя `u:xxxxxxxx`, счётчики, ссылка на карточку |

Гейт держится на трёх вещах:

1. **Белый список** (`safe-payload.ts`): письмо собирается из перечисленных полей, а не «очищается» от лишних. Новое поле в `CaptureContext` не уйдёт наружу, пока его не впишут туда руками.
2. **Очистка сообщения** (`normalize.ts`). Drizzle кладёт в текст ошибки параметры запроса (`params: Иван,+7916…,ivan@mail.ru`), Postgres — нарушившее уникальность значение (`Key (email)=(…)`). Плейсхолдеры сохраняют структуру, но не значения.
3. **Журнал**: читает только суперадминистратор; в СПИСКЕ группа `raw` вырезается хуком `afterRead` (при `findMany`) — её нет ни в админке, ни в `GET /api/error-events`; в КАРТОЧКЕ одной записи видно всё. Создавать, править и удалять записи из админки нельзя.

Инвариант закреплён тестом `tests/observability/safe-payload.test.ts`: ошибки с ФИО, телефонами, адресами, ИНН, IP, JWT прогоняются до отрендеренного письма, и ни одна подстрока не имеет права в нём встретиться.

⚠ Без пересмотра правовой части нельзя: добавлять в `SafeAlert` `userId`, `ip`, `userAgent`, `http.path`, `extra`, сырые сообщение/стек; отправлять `error.message` вместо очищенного; выносить белый список или правила очистки в админку; добавлять канал доставки во внешний сервис (мессенджер и т. п.).

## Точки перехвата

| Что | Где |
|---|---|
| рендер страницы, Route Handler, Server Action, proxy — всё, что Next поймал сам | `instrumentation.ts` → `onRequestError` |
| 5xx REST/GraphQL/админки Payload | `payload/hooks/captureAfterError.ts` (`hooks.afterError`) |
| роуты, сами превращающие исключение в 500 | `app/api/**`, `app/feed/yandex.xml` — рядом с `console.error` |
| неожиданные ошибки Server Actions | contact, feedback, restock, promo, reviews; вся авторизация — через `logUnexpectedAuthError` |
| окончательно упавшая задача воркера | `modules/restock/worker.ts`, `modules/account-deletion/worker.ts` |
| необработанное исключение / отвергнутый промис | веб: `process.ts` (Next процесс не роняет, поведение не меняется); воркеры: фиксация → падение, как и раньше |

`console.error` рядом с точками остаётся: в него вписывается `errorId`, по которому запись находится в журнале.

Ошибки со статусом 4xx (ValidationError, Forbidden Payload), долетевшие до общего catch, пишутся как `warning`: это отказ в запросе, а не сбой.

## Правила писем

| Событие | Что происходит |
|---|---|
| ошибка встретилась впервые | письмо сразу, со стеком |
| повтор в паузе | считается, письма нет (`notifiedReason: cooldown`) |
| пауза истекла | письмо-сводка: повторов, первое/последнее, сколько скрыто |
| каждая следующая отправка | пауза удваивается: 1 мин → 2 → 4 → … → 6 ч |
| тишина 6 ч | ошибка снова считается новой |
| 100-й, 1000-й, 10000-й повтор | пробивает паузу |
| 20 писем в час на весь сайт | потолок; последнее письмо говорит, что лимит исчерпан |
| предупреждения | по умолчанию не отправляются, только журнал |
| 09:00 МСК каждый день | суточная сводка — приходит и при нуле ошибок: её **отсутствие** и есть тревога |

Отпечаток — sha256 от источника, модуля, класса, кода, **очищенного** сообщения и трёх верхних собственных кадров (файл + функция, **без номера строки**): одна и та же ошибка не становится «новой» от правки выше по файлу или от другого email в тексте.

Настраивается в админке: «Система → Оповещения об ошибках» (только суперадмин). Адрес — только переменной окружения.

## Окружение

| Переменная | |
|---|---|
| `ERROR_ALERT_EMAIL` | куда слать письма; несколько — через запятую. Не задана — только журнал |
| `ERROR_LOG_RETENTION_DAYS` | срок хранения журнала, по умолчанию 90; чистит суточная задача |
| `EMAIL_ENABLED=false` | как и для прочих писем: ничего не отправляется, в журнале — «EMAIL_ENABLED=false» |

## Почему письма отправляет веб-приложение

`restock-worker` стоит только в сети `data`, без выхода наружу. Воркеры ставят письмо в очередь `error-alerts`, а разбирает её обработчик, запущенный из `instrumentation.ts`. Если Redis недоступен, письмо уходит прямо из процесса, поймавшего ошибку (из restock-worker тогда не уйдёт — запись в журнале при этом есть).

## Как ведёт себя при отказах

| Отказ | Поведение |
|---|---|
| Postgres недоступен | записи нет, письмо всё равно уходит (без ссылки на карточку) |
| Redis недоступен | счётчики в памяти процесса, письмо помечено «по одному процессу»; очереди нет — отправка сразу |
| SMTP 5xx | постоянный отказ, отметка в журнале |
| SMTP недоступен | ретраи EmailService внутри трёх попыток очереди с нарастающей паузой |
| глобал не читается | умолчания; неудача кэшируется на 15 с |

## Чего модуль не ловит

OOM-kill и segfault (обработчик не выполняется), падение до `register()`, edge-рантайм, ошибки в браузере (несут адрес страницы и User-Agent — их сбор требует согласия на аналитику), отказ самой доставки писем (иначе недоступная почта слала бы письма о недоступной почте). Первые три закрывает суточная сводка: не пришла — сайт лежит.

## Читаемость стеков веб-процесса

Три части, каждая по отдельности бесполезна: `experimental.serverSourceMaps` в `next.config.ts`, собственное сопоставление в `source-maps.ts` (Next занимает `Error.prepareStackTrace`, поэтому `--enable-source-maps` не помогает) и `scripts/prepare-source-maps.ts` в Dockerfile (standalone-трассировка не переносит `.js.map`). Если сборка упрётся в память — выключать флаг, остальное тогда ничего не делает.
