# Аналитика заказов

Страница `/admin/orders/analytics` в админке Payload. Вход — только кнопка
«Аналитика заказов» на списке заказов, пункта меню нет.

- `admin/` — страница (view Payload, кнопка, графики на SVG, разделы).
- `server/` — SQL-агрегаты и эндпоинт `GET /api/orders/analytics`.
- `lib/` — словари, разбор параметров, право доступа. Без базы и React.

## Доступ

`canViewOrderAnalytics` (`lib/access.ts`) — персонал из коллекции `admins` с
ролью `admin` или `superadmin`. Проверяется в эндпоинте (401 гостю, 403
остальным), на странице и на кнопке. Покупатель с `role=superadmin` не проходит:
решает коллекция учётной записи. Раздел считается в транзакции «только чтение»
на снимке базы и с ограничением времени запроса.

## Определения

| Показатель | Как считается |
| --- | --- |
| Дата заказа | `created_at` в поясе Europe/Moscow |
| Оформлено | все заказы, включая отменённые |
| Заказы, выручка | действующие: статус не `cancelled` и не `refunded` (правило `isVoidOrderStatus`) |
| Выручка | сумма `pricing.total` действующих заказов |
| Товарная выручка | сумма `orders_items.total_price`: со скидкой товара, до скидки корзины и промокода. Между товарами скидки заказа не делятся, разница показана строкой сверки |
| Единицы | сумма `quantity`. Позиции — строки заказа |
| Клиент | `orders.user_id`. Заказ без покупателя показан отдельно и никому не приписан |
| Новый клиент | первый действующий заказ за всю историю попал в период. История берётся без фильтров отчёта |
| Повторный заказ | действующий заказ периода, не первый у клиента |
| Доля с повторной покупкой | клиенты периода с двумя и более действующими заказами к концу периода |
| Тип покупателя | нет организации — физлицо. Организация: ИНН 12 цифр или ОГРНИП 15 — ИП; ИНН 10 или ОГРН 13 — юрлицо; иначе «тип не определён». Реквизиты берутся из снимка заказа, затем из связанной организации |
| Тип клиента | один раз, по последнему заказу периода |
| Регион | `delivery.address.region` без учёта регистра. Самовывоз и пустой регион — отдельные значения. Адрес из `street` не разбирается. У заказов удалённых аккаунтов адрес очищен, они в «Регион не указан» |
| Город | `city`, затем `settlement`, без типа: «г Калуга» и «Калуга» совпадают |
| ABC | товары по убыванию выручки: A — накоплено до 80%, B — до 95%, остальное C |
| Сравнение | «предыдущий» — столько же дней сразу перед периодом, «прошлый год» — те же даты |

## Воронка: что известно, а что нет

Этап действующего заказа определяется текущим статусом. Этап отменённого — только
историей статусов, а её пополняют оформление и отмена покупателем: смена статуса
из админки туда не пишется (`orders.service.ts`). Поэтому для отмен показан
последний зафиксированный этап, реальный мог быть позже, а время этапов считается
только по заказам с такой историей. Страница говорит об этом прямо.

Воронки «просмотр → корзина → оформление» нет намеренно: события копит
Яндекс.Метрика, а корзина в базе хранит только текущее состояние. Корзины показаны
снимком, просмотры и подписки — счётчиками за всё время, с такой подписью.

## Проверка

```bash
pnpm test:order-analytics
```

Интеграционный набор создаёт данные в транзакции и откатывает её. Часть ответов
посчитана вручную, часть — случайный набор, который сверяется с независимым
расчётом на JS. В наборе нужны даты от 2015 года: раньше Москва меняла смещение,
и время вида `+03:00` могло оказаться уже в другом дне.
