админке, доставка в реальном времени, заготовки ответов, ETA, уведомления.
Составлен 11.10.2026 по фактическому состоянию кода. Отмечать `[x]` по мере
выполнения; принятые решения — в разделе 1, менять их только осознанно.

## 1. Архитектурные решения (зафиксировано)

| Вопрос | Решение | Почему |
|---|---|---|
| Транспорт | **Socket.IO 4.8** (`socket.io` / `socket.io-client` 4.8.4) | Next 16 (`output: "standalone"`, `server.js`) не держит WebSocket в Route Handlers. Socket.IO даёт переподключение, комнаты, ack, heartbeat и **откат на long-polling** — у B2B-клиентов корпоративные прокси часто режут WS. Голый `ws` заставил бы писать всё это самим |
| Где живёт сокет-сервер | **Отдельный процесс `support-gateway`** (отдельный контейнер) | Рестарт веб-приложения не рвёт чаты; тот же паттерн, что `restock-worker` |
| Межпроцессная доставка | Redis pub/sub: `@socket.io/redis-adapter` 8.3 в gateway, `@socket.io/redis-emitter` 5.1 в app и worker | Redis уже есть; pub/sub ничего не хранит → не конфликтует с `maxmemory-policy volatile-ttl`; app/worker шлют события в комнаты, не будучи сокет-серверами |
| Источник истины | **Postgres**; сокет — только доставка | Любой разрыв лечится досинхронизацией по `seq` |
| Порядок и дедупликация | `seq` на диалог (монотонный) + `clientMessageId` (UUID v7) с уникальным индексом | Идемпотентная повторная отправка, точная досинхронизация «всё после seq N» |
| Горячий путь записи | Сырой SQL через `payload.db.drizzle` в `*.db.ts` (как `promo-redemptions.db.ts`) в одной транзакции | Нужны атомарные `last_seq + 1`, `ON CONFLICT DO NOTHING`, условный claim. Хуки коллекций на сообщениях **не использовать** (они не видят SQL — память `product-status-sql-vs-versions`); все побочные эффекты — в сервисном слое |
| Схема/админ-CRUD | Коллекции Payload (заготовки, настройки, диалоги на чтение) | Админка для заготовок и настроек бесплатно |
| Консоль менеджера | **Кастомный view в админке Payload** `/admin/support` | Менеджеры уже живут в админке на `admin.npo-polet.ru`, авторизация `admins` уже есть |
| Аутентификация сокета | Cookie `payload-token` в handshake → `payload.auth({ headers })` | Без токенов в query string. Хосты разные, cookie host-only → на витрине приходит токен `users`, в админке — `admins` |
| Модель диалога | **Один активный диалог на пользователя** (как мессенджер); после `resolved` новое сообщение в течение 7 дней переоткрывает его, позже — новый диалог | Проще виджет, вся история под рукой у менеджера |
| Контекст (заказ/товар) | Хранится **на сообщении**, не на диалоге | В одном диалоге клиент спрашивает про разные заказы |
| Распределение | Общая очередь + авто-назначение наименее загруженному доступному менеджеру; атомарный claim | Второй менеджер подключается одной галочкой, нагрузка делится сама |
| Менеджер | **Любой сотрудник `admins` (admin/superadmin)**, без лимитов | Решение владельца. На `admins` только «как видит покупатель» (имя, фото) и темы |
| Шифрование | **Конвертное AES-256-GCM:** мастер-ключ только в `SUPPORT_ENCRYPTION_KEYS`; ключ данных на каждый диалог и каждое вложение, в базе — обёрнутым; AAD привязывает шифртекст к диалогу, номеру, виду и автору | Дамп/бэкап базы, снимок диска, SQL-доступ без приложения — переписку не читают. Смена мастер-ключа — переобёртка ключей (`pnpm support:rotate-keys`), а не перешифровка всего. От взлома самого приложения не защищает (сквозное «только у клиента» невозможно: читают несколько менеджеров) |
| Что шифруется | Текст, контекст и документы сообщения (один JSON-конверт), комментарий к оценке, файлы вложений и их исходные имена | Открыто только служебное: диалог, номер, вид, автор, время, тип/размер файла, метки |
| Текст переписки в SQL | **Никогда**, даже параметром запроса: подбор заготовок — русский стеммер Snowball в процессе приложения (`lib/stem-ru.ts`), не `to_tsvector` | Иначе текст оседал бы в журнале запросов и `pg_stat_statements` |
| Вложения | **Не upload-коллекция Payload**: модуль сам проверяет сигнатуру, перекодирует изображения sharp, шифрует и отдаёт с sandbox-CSP | Payload хранит файл как есть; `image-size` (открытая уязвимость) в пути покупательских файлов не участвует |
| Фоновые задачи | BullMQ, очередь `support`, процесс `support-worker` | SLA, автозакрытие, статистика ETA, хранение 3 года, уборка файлов (писем покупателю нет) |
| Сторонний SaaS (Jivo и пр.) | Нет | ПД не уходят третьим лицам, нужна связка с заказами, компаниями и корзиной |
| ИИ-черновики ответов | Не в v1 | Передача ПД зарубежному провайдеру — вопрос 152-ФЗ, отдельное решение; плюс противоречит шифрованию |
| Поиск по тексту переписки | **Нет** — только по покупателю, email, меткам, № | Текст зашифрован; поиск потребовал бы держать его расшифрованным |

Процессы и потоки:

```
витрина (npo-polet.ru)      админка (admin.npo-polet.ru)
   │ wss /realtime                │ wss /realtime
   └──────── nginx ───────────────┘
              │ 127.0.0.1:3005
        support-gateway (Socket.IO + Payload Local API)
              │            ▲ redis-adapter / redis-emitter
   Postgres ◄─┤            │
              │       app (Next) ── emitter (смена статуса заказа, блокировка, ответ из админки)
              │       support-worker ── emitter + письма (SMTP)
```
