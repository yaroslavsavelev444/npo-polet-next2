# Чат поддержки

Переписка авторизованного покупателя с менеджером: виджет на витрине, консоль
в админке (`/admin/support`), отчёты (`/admin/support/reports`). История
решений и что сделано — в [CHECKLIST.md](CHECKLIST.md); выкладка и ключ — в
разделе «Чат поддержки» [deploy/README.md](../../../deploy/README.md).

## Архитектура

```
браузер покупателя ─┐                         ┌─ Next (app/api/support/*)
  виджет (widget/)  │  wss /realtime/  ┌──────┴──────┐  REST: история, вложения,
консоль менеджера ──┼────────────────▶ │ support-     │  счётчики, отчёты
  (admin/console/)  │                  │ gateway      │
                    │                  │ (Socket.IO)  │──▶ Postgres — источник правды
                    │                  └──────┬───────┘──▶ Redis — адаптер, присутствие,
                    │                         │              лимиты, статистика
                    └─────────────────────────┘
```

- **Шлюз** (`gateway.ts`, `server/gateway/`) — отдельный процесс: standalone
  Next не держит WebSocket, а выкладка сайта не должна рвать переписки. В нём
  же раз в минуту/5 минут/час идут периодические задачи (`server/periodic.ts`):
  переназначение и эскалация, статистика ответа, автозакрытие, срок хранения,
  уборка файлов. Каждая — под блокировкой в Redis.
- **Сервис** (`server/support.service.ts`) — вся логика; шлюз, HTTP-роуты и
  тесты зовут его, а не базу. События уходят через `Broadcaster`: в шлюзе — сам
  `io`, в Next — `@socket.io/redis-emitter`.
- **Комнаты**: покупатель только в `user:{id}`; менеджеры — `staff`,
  `admin:{id}` и `conv:{id}` открытого в консоли диалога.
- **Порядок сообщений** — `seq` диалога под блокировкой строки; повтор с тем же
  `clientMessageId` возвращает уже сохранённое. После разрыва клиент зовёт
  `sync` с последним известным `seq`.
- **Шифрование** (`server/crypto.ts`, `message-codec.ts`): текст, контекст,
  комментарий к оценке, файлы и их имена — AES-256-GCM ключом диалога, ключ
  диалога обёрнут мастер-ключом из `SUPPORT_ENCRYPTION_KEYS`. В SQL, логи,
  письма и уведомления текст переписки не попадает. Обезличивание = удаление
  ключа диалога (`server/maintenance.ts`).

| Каталог | Что там |
|---|---|
| `lib/` | общее для клиента и сервера: события и DTO, zod-схемы, стеммер, заготовки, автоссылки |
| `server/` | сервис, доступ к БД, шлюз, ETA, распределение, присутствие, уведомления, отчёты |
| `widget/` | кнопка и окно чата на витрине, `AskManagerButton`, `openSupportChat()` |
| `admin/` | консоль, пункт меню со счётчиком, отчёты |

Коллекции и настройки — в `src/payload/`: `SupportConversations`,
`SupportMessages`, `SupportAttachments`, `SupportCannedResponses`, глобал
`SupportSettings`; группа `support` в `Admins`, `supportChatBanned` в `User`.

## Как добавить менеджера

Менеджер — любой администратор. Создать учётку в «Администраторы» — и всё: она
появится в консоли и в распределении. В группе полей «Чат поддержки» учётки
можно задать имя для покупателей (иначе — обычное имя), аватар и темы, по
которым менеджер — специалист (такие диалоги достаются ему в первую очередь).
Лимитов на число диалогов нет: в пик нагрузка делится между всеми, кто «на
месте», — меньше открытых диалогов, затем дольше без нового.

«На месте» — только с открытой консолью и переключателем «На месте»; без
действий 10 минут — «отошёл», закрыл вкладку — «не в сети» через 90 секунд.
Диалог назначенного, который отошёл, через «Вернуть в очередь, если
назначенный молчит» уходит другому; если отдать некому и срок вышел — письмо
персоналу (шаблон `support-staff-alert`, без текста переписки).

## Как написать заготовку с триггерами

Админка → «Заготовки ответов»:

- **Ярлык** — команда в консоли: `/серт` + Enter вставляет текст;
- **Текст** — с переменными `{{имя}}`, `{{менеджер}}`, `{{номерЗаказа}}`;
  незаполненная переменная не уйдёт скобками — консоль подсветит, чего не
  хватило;
- **Фразы-триггеры** — когда покупатель пишет похожее, консоль сама
  предлагает заготовку. Слова сравниваются по основе (стеммер Snowball):
  триггер «сертификат» ловит «сертификаты», «сертификатов». Фраза из
  нескольких слов срабатывает, когда в сообщении есть все слова в любом
  порядке. Служебные слова и приветствия не учитываются — триггер «здравствуйте
  есть» бесполезен;
- **Файлы** — документы из медиатеки уходят покупателю вместе с ответом;
- **Темы** и **Видимость** (для всех / личная) сужают, кому и где подсказывать.

Сколько раз заготовку подсказали и использовали — в её карточке и в отчётах.

## Как включить и выключить

Админка → глобал «Чат поддержки»:

- **Чат включён для всех покупателей** — главный рубильник. Пока выключен,
  кнопки нет нигде, кроме покупателей из **Пилотной группы**.
- **Рабочее время** — интервалы по дням со своим сроком ответа (будни 15 мин,
  выходные 60), нерабочие дни. Вне расписания покупатель получает один
  автоответ на окно и видит, когда ответят.
- **Распределение** — авто или вручную, срок первого ответа, возврат в очередь.
- **Жизненный цикл** — переоткрытие и автозакрытие.

Настройки кэшируются на 30 секунд в каждом процессе (Next и шлюз).

Отдельному покупателю писать в чат можно запретить переключателем в правой
панели консоли — его сокеты закрываются сразу.

## Как отлаживать локально

```bash
# .env: SUPPORT_ENCRYPTION_KEYS=v1:<openssl rand -base64 32>,
#       SUPPORT_GATEWAY_PUBLIC_URL=http://localhost:3005
pnpm dev
pnpm support:gateway
```

Демо-данные (менеджер, покупатель в пилотной группе, заготовка, диалог;
пароли — в `db/support-demo.json`):

```bash
node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --experimental-strip-types --import ./tests/support/next-subpath-resolver.mjs scripts/seed-support-demo.ts
```

Тесты:

```bash
pnpm test:support-chat
```

```bash
pnpm test:e2e:support
```

```bash
pnpm test:support-chat:load
```

- `test:support-chat` — unit, интеграционные и сокетные, на настоящих
  Postgres и Redis; расписание подменяется и восстанавливается;
- `test:e2e:support` — Playwright: покупатель и менеджер в двух контекстах,
  плюс сценарий с заблокированным WebSocket (long-polling); сиды —
  `scripts/seed-support-e2e.ts`;
- `test:support-chat:load` — 300 сокетов и 10 сообщений/с против запущенного
  шлюза, порог доставки p95 < 300 мс.

Подводные камни:

- шлюз и скрипты — голым Node с резолвером (`--import
  ./tests/support/next-subpath-resolver.mjs`), не `tsx`;
- менеджер и покупатель в одном браузере не уживаются: у обеих коллекций
  cookie `payload-token`. Для покупателя в админском браузере —
  `POST /api/admins/logout`, затем cookie покупателя;
- `/profile/*` требует ещё cookie `session-id`;
- окно чата прячется на `/checkout` и `/auth`; открыть с любой страницы —
  `?chat=open`;
- в dev кнопку React Query Devtools сдвинули влево — справа внизу кнопка чата;
- `/realtime/health` отдаёт число сокетов и память шлюза.
